# สรุปโครงการ Sell Game 2 เพื่อจัดทำสไลด์นำเสนอ

จัดทำวันที่ 20 กันยายน 2026 จากโค้ดและเอกสารในโปรเจกต์

เนื้อหา 15 หัวข้อสำหรับนำเสนอ พร้อมภาคผนวก บันทึกผู้พูด และภาพประกอบที่แนะนำ ผลทดสอบเป็นข้อมูลจากรายงานเดิม ไม่ได้รันใหม่ในงานนี้

## 01. ภาพรวมโครงการ

**ใจความสำคัญ:** ร้านบัญชีเกมที่เชื่อมการซื้อ เครดิต และการส่งมอบไว้ในระบบเดียว

- Sell Game 2 เป็นเว็บร้านขายบัญชีเกม มีเอกสารเดิมเรียกระบบว่า Mizuki Shop และใช้แนวทางภาพ Game Vault ในงาน UX/UI
- แกนหลักประกอบด้วยหน้าร้าน ระบบสมาชิก Wallet การซื้อและรับข้อมูลบัญชีเกม ระบบสุ่มรางวัล และหลังบ้านผู้ดูแล
- มีประวัติธุรกรรม การแจ้งเตือน รายงานยอด และช่องทางสนทนากับร้าน เพื่อให้ติดตามงานหลังการขายได้
- เอกสารนี้สรุปจากโค้ด การตั้งค่า และรายงานในโปรเจกต์ ณ 20 กันยายน 2026 ไม่ใช่รายงานรายได้หรือจำนวนผู้ใช้งานจริง

**บันทึกผู้พูด:** เปิดด้วยภาพรวมว่าโครงการครอบคลุมตั้งแต่เลือกสินค้าไปจนถึงรับข้อมูลและขอความช่วยเหลือ ชื่อแบรนด์ควรเลือกใช้ชื่อเดียวกันเมื่อทำสไลด์จริง

**ภาพที่แนะนำ:** ภาพหน้าแรก + แผนภาพ หน้าร้าน > Wallet > ซื้อ/สุ่ม > คลังของฉัน

**แหล่งอ้างอิงในโปรเจกต์:** routes/web.php; docs/ux-ui-design.md

## 02. ที่มาและวัตถุประสงค์

**ใจความสำคัญ:** ลดความกระจัดกระจายของขั้นตอนซื้อขายและการติดตามรายการ

- โจทย์ที่ระบบมุ่งแก้: การตรวจเงิน สถานะสินค้าคงเหลือ และการส่งข้อมูลบัญชีต้องสัมพันธ์กัน มิฉะนั้นอาจขายซ้ำหรือเพิ่มเครดิตซ้ำ
- รวมการเลือกซื้อ การชำระด้วยเครดิต และการรับข้อมูลบัญชีไว้ในเส้นทางใช้งานเดียว
- ให้ผู้ดูแลตรวจเติมเงิน จัดการสินค้า และค้นประวัติได้จากหลังบ้าน
- เพิ่มความชัดเจนแก่ลูกค้าด้วยสถานะรายการ เหตุผลปฏิเสธ และบทสนทนาติดตามปัญหา

**บันทึกผู้พูด:** ส่วนนี้เป็นการสังเคราะห์วัตถุประสงค์จากความสามารถของระบบ ยังไม่มีข้อมูลสำรวจผู้ใช้หรือสถิติลดเวลาทำงาน จึงไม่ควรนำเสนอเป็นผลวิจัยที่วัดแล้ว

**ภาพที่แนะนำ:** แผนภาพปัญหา 3 จุด: เงิน / สต็อก / การส่งมอบ

**แหล่งอ้างอิงในโปรเจกต์:** app/Services/StoreService.php; docs/topup-review-history.md

## 03. ผู้ใช้และขอบเขตปัจจุบัน

**ใจความสำคัญ:** แยกผู้เยี่ยมชม สมาชิก และผู้ดูแลร้าน

- ผู้เยี่ยมชม: ดูหมวดหมู่ บัญชีเกม กาชา ข่าว และส่งคำถามถึงร้าน โดยติดตามบทสนทนาผ่านลิงก์ที่มีลายเซ็น
- สมาชิก: เติม Wallet ซื้อบัญชีเกม สุ่มรางวัล เปิดประวัติและคลังของตน อ่านแจ้งเตือน เปลี่ยนรหัสผ่าน และสนทนากับร้าน
- ผู้ดูแล: จัดการสมาชิก หมวดหมู่ บัญชีเกม กล่องสุ่ม ตรวจเติมเงิน ดูรายงาน ตอบข้อความ และตั้งค่าร้าน/แบนเนอร์
- config/store.php กำหนด service_catalog_enabled=false และ demo_mode=true: ระบบสินค้า/งานบริการมีโครงสร้างรองรับ แต่ปิดทางเข้าใช้งานที่เกี่ยวข้องอยู่

**บันทึกผู้พูด:** ย้ำว่าระบบบริการไม่ใช่ความสามารถที่เปิดอยู่ในขอบเขตสาธิตปัจจุบัน และไม่ควรอ้างว่าระบบพร้อม production เพียงเพราะมีหน้าเว็บครบ

**ภาพที่แนะนำ:** ตารางสิทธิ์ 3 กลุ่ม + ป้ายระบบบริการยังปิด

**แหล่งอ้างอิงในโปรเจกต์:** routes/web.php; config/store.php; app/Http/Middleware/EnsureServiceCatalogEnabled.php

## 04. เส้นทางใช้งานของลูกค้า

**ใจความสำคัญ:** จากเลือกบัญชีเกมจนถึงรับข้อมูลและติดตามหลังการขาย

- 1. เลือกหมวดหมู่ ค้นหา และอ่านรายละเอียดบัญชีเกม ราคา และสถานะสินค้า
- 2. สมัครหรือเข้าสู่ระบบ หากเครดิตไม่พอให้ไปหน้า Wallet เพื่อส่งรายการเติมเงิน
- 3. รอผู้ดูแลตรวจหลักฐาน เมื่ออนุมัติจึงได้รับเครดิตสำหรับใช้ในร้าน
- 4. ยืนยันซื้อ ระบบตรวจยอดและสต็อก หักเครดิต บันทึกประวัติ และเปลี่ยนสินค้าเป็น sold
- 5. เปิดข้อมูลส่งมอบจากรายการซื้อ/คลังของตน และติดต่อร้านโดยอ้างอิงรายการเมื่อมีปัญหา

**บันทึกผู้พูด:** ตัวอย่างใน integration test ใช้เติมเครดิตจำลอง 300 ซื้อบัญชี 199 แล้วเหลือ 101 ตัวเลขนี้เป็นข้อมูลทดสอบ ไม่ใช่รายการเงินจริง

**ภาพที่แนะนำ:** ผังลำดับ 5 ขั้น หรือภาพหน้าจอ 3 หน้า: สินค้า / Wallet / ส่งมอบ

**แหล่งอ้างอิงในโปรเจกต์:** docs/store-journey-testing.md; app/Services/StoreService.php

## 05. Wallet และการตรวจเติมเงิน

**ใจความสำคัญ:** เพิ่มเครดิตเมื่ออนุมัติ พร้อมป้องกันคำขอและหลักฐานซ้ำหลายชั้น

- หน้า Wallet รองรับช่องทาง PromptPay และ TrueMoney ตามขั้นตอนส่งหลักฐานให้ผู้ดูแลตรวจ ยังไม่ใช่การยืนยันเงินเข้าอัตโนมัติจากผู้ให้บริการ
- รายการใหม่อยู่สถานะ pending; การอนุมัติจึงเพิ่มเครดิต ส่วนการปฏิเสธต้องมีเหตุผลและไม่เพิ่มยอด
- ใช้ request_id และ fingerprint เพื่อให้การส่งคำขอเดิมซ้ำคืนรายการเดิม และปฏิเสธเมื่อใช้รหัสเดิมกับข้อมูลที่เปลี่ยน
- มี hash ไฟล์สลิปและการจองเลขอ้างอิงการโอนตามช่องทาง เพื่อป้องกันการใช้ซ้ำตามเงื่อนไขระบบ
- เก็บผู้ตรวจ เวลา สถานะก่อน/หลัง และเหตุผล สลิปรับ JPG/PNG/WEBP ขนาดไม่เกิน 5 MB

**บันทึกผู้พูด:** กลไกกันซ้ำช่วยรักษาความถูกต้องของรายการ แต่ไม่พิสูจน์ว่าเงินเข้าจริง ผู้ดูแลยังต้องตรวจยอดรับจากแหล่งที่เชื่อถือได้ ประวัติการตรวจไม่ใช่ audit log ครอบคลุมทั้งร้าน

**ภาพที่แนะนำ:** ผัง pending > success หรือ rejected + ภาพหน้าตรวจสลิป

**แหล่งอ้างอิงในโปรเจกต์:** docs/topup-idempotency.md; docs/topup-review-history.md; docs/system-audit-fixes-2026-09-17.md

## 06. การซื้อและส่งมอบบัญชีเกม

**ใจความสำคัญ:** ผูกการตัดเครดิตกับการขายสินค้าในธุรกรรมเดียว

- StoreService ตรวจยอด Wallet สถานะ available และประวัติว่าบัญชีนั้นยังไม่เคยถูกขาย
- ใช้ database transaction และ lockForUpdate กับแถวผู้ใช้และบัญชีเกม เพื่อลดปัญหาคำขอซื้อชนกัน
- เมื่อสำเร็จ สร้างประวัติซื้อ ตัดเครดิต เปลี่ยนสินค้าเป็น sold และบันทึก WalletTransaction
- ข้อมูลบัญชีเกมและสำเนาข้อมูลส่งมอบถูกเข้ารหัส ผู้ซื้อเปิดข้อมูลได้จากเส้นทางที่ตรวจสิทธิ์
- มีการป้องกันนำบัญชีที่มีประวัติขายแล้วกลับมาเปิดขาย และแจ้งเตือนผู้ซื้อ/ผู้ดูแลเมื่อเกิดรายการ

**บันทึกผู้พูด:** อธิบาย transaction ว่าเป็นชุดงานที่ต้องสำเร็จร่วมกัน หากขั้นตอนล้มเหลวจะย้อนการเปลี่ยนแปลงในฐานข้อมูล ไม่กล่าวอ้างว่าการเข้ารหัสป้องกันการเข้าถึงได้ทุกกรณี

**ภาพที่แนะนำ:** แผนภาพ ตรวจ > ล็อก > ตัดเครดิต + sold + ประวัติ > ส่งมอบ

**แหล่งอ้างอิงในโปรเจกต์:** app/Services/StoreService.php; app/Models/GameAccount.php; docs/review-followup-2026-09-17.md

## 07. ระบบสุ่มรางวัล Gacha

**ใจความสำคัญ:** สุ่มจากรางวัลที่ยังมีสิทธิ์ออก และเก็บผลสำหรับคำขอเดิม

- มีรูปแบบนำเสนอ cards / wheel / box โดยผลรางวัลคำนวณที่ฝั่งเซิร์ฟเวอร์
- รางวัลเป็นเครดิต Wallet หรือบัญชีเกมที่ยัง available; คัดเฉพาะรายการที่มี drop_rate มากกว่า 0
- โอกาสออกคิดจากน้ำหนักของรางวัลเทียบผลรวมน้ำหนักที่ใช้ได้ ณ เวลาสุ่ม จึงเปลี่ยนได้เมื่อชุดรางวัลเปลี่ยน
- request_id ช่วยคืนผลสุ่มเดิมเมื่อส่งซ้ำ โดยไม่หักค่าสุ่มหรือจ่ายรางวัลซ้ำ; มี receipt และประวัติการสุ่ม
- เมื่อได้บัญชีเกม ระบบอาจเติมรางวัลทดแทนจากหมวดเดียวกันหากมีบัญชีที่เข้าเงื่อนไข พร้อมรักษารายการเดิมเพื่ออ้างอิงประวัติ

**บันทึกผู้พูด:** การเลือกการ์ดหรือภาพเคลื่อนไหวเป็นการนำเสนอผล ไม่ควรอธิบายว่าตำแหน่งที่เลือกเปลี่ยนน้ำหนักรางวัล ตัวอย่างน้ำหนัก 20 และ 80 หมายถึงสัดส่วนประมาณ 20% และ 80% เมื่อมีเพียงสองรางวัลนั้น

**ภาพที่แนะนำ:** ภาพ 3 โหมด + ตัวอย่างสัดส่วนน้ำหนักรางวัล

**แหล่งอ้างอิงในโปรเจกต์:** app/Services/StoreService.php; resources/views/gacha/show.blade.php; docs/review-followup-2026-09-17.md

## 08. หลังบ้านและรายงาน

**ใจความสำคัญ:** รวมงานประจำร้านและแยกประเภทความเคลื่อนไหวของเครดิต

- จัดการข้อมูลสมาชิก สินค้าบัญชี หมวดหมู่ กล่องสุ่ม รายการรางวัลและน้ำหนัก ตลอดจนการตั้งค่าร้านและช่องทางติดต่อ
- หน้าตรวจเติมเงินแยกจากประวัติอนุมัติ/ปฏิเสธ เพื่อค้นรายการและผู้ดำเนินการย้อนหลัง
- รายงานเลือกวันนี้ เดือนนี้ ช่วงวันที่ หรือทั้งหมดได้ และมีเส้นทาง export รวมทั้งรายการขายดี
- ยอดรวมตามโค้ด = ขายบัญชี + งานบริการ + ค่าสุ่ม; ยอดสุทธิในรายงานหักคืนเงินงานบริการและเครดิตรางวัลสุ่ม
- ยอดเติม Wallet แสดงแยกจากยอดขาย จึงไม่ควรนำยอดเติมมารวมซ้ำเป็นรายได้จากการขาย

**บันทึกผู้พูด:** ยอดสุทธิในรายงานนี้ไม่ใช่กำไรทางบัญชี เพราะยังไม่ได้หักต้นทุนสินค้าและค่าใช้จ่ายทั้งหมด ส่วนงานบริการอาจใช้กับประวัติเก่าหรือเมื่อเปิดฟีเจอร์ในอนาคต

**ภาพที่แนะนำ:** ภาพรายงาน + กล่องนิยามยอดขาย/ยอดเติม/เครดิตรางวัล

**แหล่งอ้างอิงในโปรเจกต์:** routes/web.php; app/Services/SalesReportService.php

## 09. การช่วยเหลือลูกค้าและการแจ้งเตือน

**ใจความสำคัญ:** ติดตามปัญหาเป็นบทสนทนาพร้อมบริบทของรายการ

- แยกประเภทเรื่องเป็นสอบถามทั่วไป เติมเงินไม่เข้า ปัญหาไอดีเกม ปัญหาคำสั่งซื้อ และปัญหาสุ่มรางวัล
- สมาชิกผูกเลขอ้างอิงที่ตนมีสิทธิ์เข้าถึงกับเรื่องติดต่อได้ และอ่าน/ตอบได้เฉพาะบทสนทนาของตน
- ผู้เยี่ยมชมใช้ลิงก์ signed สำหรับติดตามและตอบกลับ ไม่ใช้เพียงอีเมลเพื่อยึดสิทธิ์บทสนทนา
- แสดงสถานะรอร้านตอบ รอลูกค้าตอบ หรือจัดการแล้ว พร้อมข้อความตอบจากผู้ดูแล
- แนบภาพได้ไม่เกิน 3 ไฟล์ต่อชุด ไฟล์ละ 2 MB ในชนิดที่รองรับ จัดเก็บเป็นไฟล์ส่วนตัวและตรวจสิทธิ์เมื่อเปิดดู

**บันทึกผู้พูด:** ส่วนสนับสนุนลูกค้ามีโค้ดและชุดทดสอบสำหรับการสนทนา การแนบภาพ และการควบคุมสิทธิ์ แต่เอกสารนี้ไม่ได้รันชุดทดสอบใหม่ จึงไม่ระบุจำนวน tests ปัจจุบันว่าได้ผ่านแล้ว

**ภาพที่แนะนำ:** ภาพห้องสนทนา + สถานะผู้ที่ต้องตอบต่อ

**แหล่งอ้างอิงในโปรเจกต์:** app/Models/ContactMessage.php; app/Services/ContactAttachments.php; tests/Feature/ContactSupportTest.php; tests/Feature/ContactConversationTest.php

**ใจความสำคัญ:** Laravel แยกหน้าจอ การรับคำขอ กฎธุรกิจ และข้อมูล

- Backend กำหนด PHP ^8.2 และ Laravel ^12.0 ใน composer.json; ใช้ Blade สำหรับหน้าเว็บ และ Eloquent สำหรับโมเดลข้อมูล
- Frontend ใช้ Vite ^7 และ Tailwind CSS ^4 ตาม package.json ร่วมกับ JavaScript สำหรับการโต้ตอบในหน้าเว็บ
- โครงสร้างหลัก: routes > middleware > controllers > services/models > database และส่งผลไปยัง Blade views
- กลุ่มข้อมูลหลัก: Users, GameAccounts, PurchaseHistories, WalletTransactions, TopupTransactions/Reviews, GachaBoxes/Items/Spins
- ข้อมูลสนับสนุน: Categories, Notifications, StoreSettings/Banners, ContactMessages/Replies/Attachments; มี Products/ServiceOrders สำหรับส่วนบริการที่ปิดอยู่

**บันทึกผู้พูด:** เลขเวอร์ชันเป็นช่วงที่ประกาศในไฟล์ dependency ไม่ใช่การอ้างว่าเป็นเวอร์ชันล่าสุด ระบบ local มีรายงานใช้ XAMPP/MariaDB ส่วน phpunit.xml ตั้ง SQLite ในหน่วยความจำสำหรับ tests

**ภาพที่แนะนำ:** แผนภาพ 4 ชั้น + ER แบบย่อ User เชื่อม Purchase/Wallet/Topup/Spin/Contact

**แหล่งอ้างอิงในโปรเจกต์:** composer.json; package.json; app/Models/; database/migrations/; phpunit.xml

## 11. UX/UI และประสิทธิภาพ

**ใจความสำคัญ:** สไตล์เกมที่ยังให้ความสำคัญกับราคา สถานะ และการอ่านบนมือถือ

- แนวทางภาพใช้พื้นเข้มสีน้ำเงิน ส้มสำหรับการกระทำหลัก และฟ้าสำหรับเครดิต/สถานะ พร้อมแผงข้อมูลและมุมโค้ง
- หน้าซื้อเน้นราคา สินค้าพร้อมขาย และปุ่มไปเติม Wallet เมื่อยอดไม่พอ; มีสถานะว่างและทางไปต่อ
- เอกสาร UX รายงานตรวจหน้าใช้งานตัวแทนที่ความกว้าง 390, 900 และ 1366 พิกเซล โดยไม่พบหน้าไหลออกแนวนอนในกรณีที่ตรวจ
- งานวันที่ 19 กันยายนเปลี่ยนภาพกาชา 3 ภาพเป็น WebP: รวมจาก 7,892,962 เหลือ 631,274 bytes ลดขนาดไฟล์ประมาณ 92%
- รายงานกาชาระบุ browser checks ที่ 390 และ 1440 พิกเซลผ่านในกรณีทดสอบ แต่ใช้ fixtures/ผลสุ่มจำลอง

**บันทึกผู้พูด:** 92% คือการลดน้ำหนักไฟล์สามภาพ ไม่ใช่การยืนยันว่าเว็บโหลดเร็วขึ้น 92% และการตรวจบางหน้าไม่เท่ากับยืนยันทุกหน้าทุกอุปกรณ์

**ภาพที่แนะนำ:** กราฟแท่งขนาดภาพก่อน/หลัง + ภาพมือถือและเดสก์ท็อป

## 12. ความถูกต้องและความปลอดภัย

**ใจความสำคัญ:** ตรวจสิทธิ์ ป้องกันรายการซ้ำ และรักษาข้อมูลสำคัญ

- เส้นทางสมาชิกตรวจ auth และ auth.session; หลังบ้านตรวจสิทธิ์ admin เพิ่ม และมี rate limit ในคำขอสำคัญ
- ใช้ transaction, row locks และ unique constraints ร่วมกับ request identity เพื่อลดการขายซ้ำ เพิ่มเครดิตซ้ำ และสุ่มซ้ำ
- เข้ารหัสข้อมูลบัญชีเกม/ข้อมูลส่งมอบ และจำกัดการเปิดสลิปกับภาพแนบส่วนตัวตามสิทธิ์
- มี security headers และ CSP ตามรายงานแก้ไขล่าสุด แต่ยังใช้ unsafe-inline จึงไม่ใช่ strict CSP
- การเปลี่ยนรหัสผ่านเกี่ยวข้องกับการหมดสิทธิ์ session เก่าผ่าน auth.session เมื่อมีการเรียกเส้นทางที่ตรวจ ไม่ได้หมายถึงลบ session ทุกเครื่องทันที

**บันทึกผู้พูด:** มาตรการที่มีเป็นการลดความเสี่ยง ไม่ใช่การรับรองว่าปลอดภัยทั้งหมด การตรวจ production ต้องครอบคลุมเว็บเซิร์ฟเวอร์ สิทธิ์ไฟล์ และการตั้งค่าจริงด้วย

**ภาพที่แนะนำ:** ตาราง 3 คอลัมน์: สิทธิ์ / ธุรกรรม / ข้อมูลส่วนตัว

**แหล่งอ้างอิงในโปรเจกต์:** routes/web.php; app/Http/Middleware/SecurityHeaders.php; docs/review-followup-2026-09-17.md; docs/production-security.md

## 14. สถานะปัจจุบันและแนวทางต่อยอด

**ใจความสำคัญ:** มีระบบหลักและหลักฐานทดสอบ แต่ยังต้องเตรียมสภาพแวดล้อมใช้งานจริง

- ความสามารถที่พบในโค้ด: ซื้อและส่งมอบบัญชี Wallet ตรวจสลิป Gacha หลังบ้าน รายงาน การแจ้งเตือน และสนทนากับร้าน
- ก่อนขึ้น production: ตั้งโดเมน/HTTPS ปิด debug ใช้ DB user จำกัดสิทธิ์ และกำหนด DocumentRoot ไป public/
- วางระบบสำรองข้อมูลและเก็บ APP_KEY แยกอย่างปลอดภัย ติดตั้งตัวเรียก scheduler และซ้อม restore ในสภาพแวดล้อมเป้าหมาย
- ตรวจซ้ำบน staging ด้วยชุดโค้ดล่าสุด ทั้งเส้นทางลูกค้า/แอดมิน สิทธิ์เข้าถึง ไฟล์ส่วนตัว และธุรกรรมพร้อมกัน
- ข้อเสนอต่อยอด: การยืนยันชำระเงินอัตโนมัติ audit log ที่ครอบคลุมขึ้น การติดตามระบบ และการวัด UX/เวลาโหลดจริง โดยยังไม่ใช่งานที่ทำเสร็จแล้ว

**บันทึกผู้พูด:** รายงาน 19 กันยายนยังกล่าวถึง warning ของตารางระบบ MariaDB บางตาราง และไม่ได้เปลี่ยน SMTP/HTTPS จึงควรนำเสนอว่าเป็นระบบที่พัฒนาและทดสอบใน local มากกว่าระบบ production ที่รับรองแล้ว

**ภาพที่แนะนำ:** แผนงาน 3 ระยะ: ตรวจล่าสุด > เตรียมเซิร์ฟเวอร์ > ทดลองใช้งาน

**แหล่งอ้างอิงในโปรเจกต์:** config/store.php; docs/production-security.md; docs/backup-restore.md; docs/gacha-performance-2026-09-19.md

## 15. บทพูดปิดและแผนสาธิต

**ใจความสำคัญ:** สรุปคุณค่าจากกระบวนการที่เชื่อมกันและตรวจสอบย้อนหลังได้

- บทพูดปิด: “โครงการนี้รวมการขายบัญชีเกม การใช้เครดิต และการส่งมอบไว้ในระบบเดียว พร้อมเครื่องมือให้ผู้ดูแลตรวจรายการและช่วยเหลือลูกค้า โดยเน้นความถูกต้องของธุรกรรมและการติดตามย้อนหลัง”
- ลำดับสาธิตแนะนำ: เปิดหน้าร้าน > เข้าระบบสมาชิก > เปิด Wallet และรายการตัวอย่าง > เปิดประวัติซื้อ/คลัง > กาชา > ติดต่อร้าน > หลังบ้านและรายงาน
- ใช้ข้อมูลจำลองหรือ staging แยกจากร้านสำหรับการซื้อ เติมเงิน อนุมัติ และสุ่มในการนำเสนอ
- แบ่งเวลาประมาณ 15-20 นาที: ภาพรวม/ผู้ใช้ 3 นาที กระบวนการ/ฟีเจอร์ 7 นาที เทคนิค/หลักฐาน 4 นาที และสาธิต/สรุป 4 นาที
- หากต้องย่อเป็น 10 สไลด์ ให้รวมภาพรวมกับวัตถุประสงค์ รวมการซื้อกับเส้นทางลูกค้า รวมหลังบ้านกับ support และรวม UX กับสถาปัตยกรรม

**บันทึกผู้พูด:** เลือกภาพหน้าจอที่ไม่มีรหัสบัญชีเกม สลิปจริง หรือข้อมูลส่วนตัว ไม่จำเป็นต้องนำเนื้อหาทุกบรรทัดขึ้นสไลด์ ใช้บันทึกผู้พูดเพื่อเก็บรายละเอียด

**ภาพที่แนะนำ:** ภาพรวมระบบหนึ่งภาพ + ประโยคปิดสั้น

**แหล่งอ้างอิงในโปรเจกต์:** สังเคราะห์จากโครงสร้างและเอกสารโครงการ
