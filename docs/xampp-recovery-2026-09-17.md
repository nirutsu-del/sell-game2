# ซ่อมฐานข้อมูล XAMPP — 17 กันยายน 2026

## ผลสุดท้าย

ใช้ XAMPP/MariaDB 10.4.32 ตัวเดิม พอร์ต 3306 และ my.ini เดิม ไม่ได้ติดตั้งฐานข้อมูลตัวใหม่หรือเปลี่ยนการเชื่อมต่อ Laravel

- ตรวจตารางทั้งเซิร์ฟเวอร์ด้วย mysqlcheck: **98 ตาราง OK**
- ทดสอบพร้อมกัน **12 กรณีผ่าน** (6 กรณี × 2 รอบ, 4 workers ต่อกรณี)
- กู้ backup ลงฐานข้อมูลแยกสำเร็จ และข้อมูลธุรกิจ/ยอด Wallet ตรงกับร้าน
- ถอดรหัสข้อมูลด้วย APP_KEY เดิมได้ 54 รายการ; ตรวจภาพ/สลิป 64 ไฟล์ผ่าน ไม่มีไฟล์ที่อ้างอิงแล้วหาย
- ทดสอบ shutdown ตามปกติและเปิดกลับสองรอบสำเร็จ หลังซ่อมรอบสุดท้าย
- หน้าแรก, login, accounts, gacha และ phpMyAdmin ตอบ HTTP 200; หน้าแรกตรวจซ้ำหลัง restart สุดท้ายได้ 200
- ไม่มี schema หรือบัญชีผู้ใช้ชั่วคราวของ concurrency/restore หลงเหลือ และปิดตัวทดสอบพอร์ต 3307 แล้ว

## หลักฐานและการซ่อม

Windows Event Log ยืนยัน mysqld.exe crash เวลา 18:08:59 ด้วย exception 0x80000003 ขณะการทดสอบก่อนหน้า ต่อมาตรวจพบ `mysql.db` ซึ่งเป็นตารางสิทธิ์ของระบบ Aria เสียหาย มี CRC errors ส่วนตาราง global_priv/tables_priv/columns_priv ผ่าน

เก็บ cold copy ของ data directory ทั้งหมดตอนเซิร์ฟเวอร์หยุด พร้อม my.ini ก่อนซ่อม แล้วสร้างสำเนาที่พอร์ต 3307 ทดลองซ่อมและทดสอบก่อนใช้กับตัวจริง

ซ่อม `mysql.db` ด้วย REPAIR TABLE และตรวจซ้ำแบบ offline ด้วย aria_chk ตอนเซิร์ฟเวอร์หยุด การซ่อมออนไลน์ของตัวจริงเคยตอบ error เรื่อง Aria log file descriptor แม้ CHECK TABLE ต่อมาผ่าน จึงไม่ถือผลครั้งนั้นเป็นหลักฐานจบงาน ได้หยุดโปรเซสที่ค้างหลัง shutdown ไม่สำเร็จ ตรวจ offline และเปิดกลับด้วย stdout/stderr ที่ส่งลงไฟล์อย่างชัดเจน จากนั้นตรวจตารางทั้งหมด ทดสอบธุรกรรม และ shutdown/restart ซ้ำจนผ่าน

เมทาดาทาของตารางเสียระบุ 4 แถว แต่การซ่อมกู้คืนได้ 0 แถว ก่อนซ่อม SCHEMA_PRIVILEGES ไม่รายงานสิทธิ์ระดับ schema อยู่แล้ว ได้เก็บ SHOW GRANTS ของทั้ง 4 บัญชี และเปรียบเทียบหลังซ่อม/หลัง restart ว่าตรงกันทั้งหมด จึงยืนยันการคงสิทธิ์ที่เซิร์ฟเวอร์รายงานได้ ไม่ได้อ้างว่ากู้แถวเสียเดิมกลับได้ครบ

ลบเฉพาะ schema ทดสอบที่เสีย `mizuki_race_e35ec1948ef6` โดยปิด FOREIGN_KEY_CHECKS เฉพาะ connection ที่ลบ แล้วเปิดกลับ ไม่ได้ลบไฟล์ InnoDB ของร้านหรือฐานข้อมูลโปรเจกต์อื่นโดยตรง ข้อมูลธุรกิจร้านเทียบกับ backup ก่อนซ่อมแล้วตรงกัน

ยังไม่ได้พิสูจน์สาเหตุรากของ crash แรกหรือยืนยันว่าอาการจะไม่เกิดอีกตลอดไป ผลยืนยันคือหลังซ่อมผ่านการตรวจและทดสอบที่ระบุข้างต้น

## การทดสอบพร้อมกัน

`php scripts/verify-concurrency.php` บน XAMPP ตัวจริงสร้างฐานข้อมูลและบัญชีชั่วคราวแยกจากร้าน:

1. ซื้อไอดีเดียวกันพร้อมกัน: ขายครั้งเดียว
2. อนุมัติ topup เดียวกันพร้อมกัน: เพิ่มเงินครั้งเดียว
3. อนุมัติคนละ topup ด้วยเลขโอนเดียวกัน: สำเร็จครั้งเดียว
4. ส่งคำขอเติมเงิน request_id เดิมพร้อมกัน: สร้างรายการเดียว
5. ส่งสลิปไฟล์เดียวกันข้ามผู้ใช้พร้อมกัน: รับครั้งเดียว
6. ส่งคำขอสุ่ม request_id เดิมพร้อมกัน: ได้ spin เดียว หักค่าสุ่มครั้งเดียวและจ่ายรางวัลครั้งเดียว

ปรับสคริปต์ให้ใช้ bcrypt cost 4 เฉพาะข้อมูลผู้ใช้จำลองในฐานข้อมูลแยก และเพิ่มกรณี spin_retry ไม่ได้เปลี่ยนการ hash รหัสผ่านของร้าน

รายงานสำเร็จ: `storage/app/concurrency-tests/report-c1d74b141348.json`
