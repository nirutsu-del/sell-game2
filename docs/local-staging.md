# Local staging — Mizuki Shop

สร้างและทดสอบวันที่ 8 กันยายน 2026 เปิดเฉพาะ loopback ที่ http://127.0.0.1:8010 ไม่ใช่เว็บไซต์ staging บนอินเทอร์เน็ต

## เปิดใช้งาน

ครั้งแรก: `php scripts/staging-setup.php` (ทำแล้ว สคริปต์จะไม่ทับฐานข้อมูลเดิม)

เปิดเซิร์ฟเวอร์จากโฟลเดอร์โปรเจกต์:

```powershell
php -S 127.0.0.1:8010 scripts/staging-router.php
```

หยุดด้วย Ctrl+C ใน terminal ที่รันเซิร์ฟเวอร์ ห้ามเปลี่ยนเป็น 0.0.0.0 หรือเปิดพอร์ตออกอินเทอร์เน็ต

บัญชีทดสอบ admin@staging.test และ buyer@staging.test ใช้รหัสผ่านสุ่มที่เก็บใน `storage/app/local-staging/credentials.json` อย่าใช้รหัสนี้กับระบบอื่น ไม่มีข้อมูลลูกค้าจริงใน staging

ตรวจการแยกข้อมูล: `php scripts/staging-check.php`

หลังแก้ frontend: `npm run build` แล้ว `php scripts/staging-check.php --sync-assets` และ reload เบราว์เซอร์

## การแยกระบบ

- ไม่โหลด .env ร้านหรือ config cache ร้าน ใช้ APP_KEY ใหม่ ฐานข้อมูล SQLite, sessions, cache, logs, uploads และ public assets แยกใต้ storage/app/local-staging
- cookie ชื่อ mizuki_local_staging แยกจากร้านจริง อีเมลใช้ log เท่านั้น
- ไม่มี QR รับเงินจริง ใช้ SVG ระบุ TEST ONLY / NOT A PAYMENT QR เพื่อทดสอบช่องแสดงภาพและ JavaScript สลับช่องทาง ไม่ได้ทดสอบการสแกนชำระเงินจริง
- ป้าย STAGING แสดงทุกหน้า รวมหลังบ้าน และโฟลเดอร์ข้อมูลถูก ignore ใน Git
- router อนุญาต static เฉพาะไฟล์รูป/CSS/JS/font ใน public staging ไม่เปิดไฟล์ฐานข้อมูล key หรือ credentials

## ผลทดสอบ

- เปิดเว็บผ่านเบราว์เซอร์จริงในแอป ตรวจ viewport 1366×900 และ 390×844
- หน้าแรกและรูปสินค้าจำลองโหลดได้ ช่องภาพ Wallet ทั้งสองช่องโหลดสำเร็จ สลับ PromptPay/TrueMoney แล้วแสดงช่องตรงตัวเลือก
- หน้า Wallet รายละเอียดสินค้า และห้องสุ่มที่ 390px ไม่ล้นแนวนอน (document scrollWidth 375px รวมพื้นที่ scrollbar)
- login/logout บัญชีผู้ซื้อและแอดมินสำเร็จ อนุมัติหนึ่งรายการ 300 เครดิตจำลอง แล้วซื้อไอดี 199 ผ่านปุ่มหน้าเว็บ ได้รับข้อมูล dummy-player-1 ยอดเหลือ 101
- ทดสอบฉากสุ่มเครดิตจำลองหนึ่งครั้ง หัก 30 คืน 5 ยอดเหลือ 76 มีผลรางวัลและประวัติหลังเปิดหน้าใหม่
- ตรวจ HTTP แยกด้วย session และ CSRF จริง: multipart เติมเงินสำเร็จ; ไม่มี CSRF ได้ 419
- GET/HEAD /.env, /scripts/staging-bootstrap.php, /storage/credentials.json ได้ 404 ส่วนภาพจำลอง /storage/promptpay.svg ได้ 200
- ชุดข้อมูลหลังทดสอบ: 2 ผู้ใช้, 4 รายการเติมเงิน (อนุมัติ 1 รอตรวจ 3), ซื้อ 1, สุ่ม 1 เก็บไว้ให้ตรวจต่อ ไม่มีการเติมเงินจริง

## ประเด็นที่ยังต้องแก้/ตรวจต่อ

อัปเดต: งานป้องกันคำขอเติมเงินซ้ำและหน้ารับรายการทำแล้ว ดู [topup-idempotency.md](topup-idempotency.md) ยืนยันใน browser ว่า redirect ไปหน้ารับรายการทันที ประเด็น 1–2 ด้านล่างเป็นผลทดสอบเดิมก่อนแก้ ส่วนการตรวจสลิปเดียวกันในคำขอใหม่ยังไม่ครอบคลุม

1. ในเบราว์เซอร์ทดสอบ เมื่อฟอร์ม POST redirect กลับ URL เดิม หน้าจอไม่แสดงผลใหม่ทันที แต่ข้อมูลถูกบันทึกแล้ว ยืนยันจากหลังบ้านและยอดเงิน ยังไม่ยืนยันสาเหตุว่าเป็นเว็บหรือเบราว์เซอร์ในแอป
2. การส่งฟอร์มเติมเงินซ้ำสร้างหลายรายการ pending ได้ (เกิดระหว่างตรวจกรณีข้างต้น) ควรเพิ่ม request id / idempotency ฝั่งเซิร์ฟเวอร์และสถานะกำลังส่งที่ปุ่ม ไม่ใช่อาศัย throttle อย่างเดียว
3. ยังไม่ยืนยันการแนบไฟล์จาก browser chooser end-to-end; PHP integration tests ตรวจอัปโหลด PNG จำลองผ่านแล้ว
4. กล่องที่มีรางวัลเครดิตอย่างเดียวแสดงป้าย “ไอดีหมดชั่วคราว” ทั้งที่ยังสุ่มเครดิตได้ ควรแยกข้อความสถานะในรายการกล่อง
5. วันที่บางหน้าประวัติยังแสดง UTC ไม่ใช่เวลาไทย ควรทำรูปแบบเวลาให้สอดคล้องกัน

ยังไม่ทดสอบอุปกรณ์มือถือจริง HTTPS SMTP ผู้ให้บริการชำระเงิน หรือ concurrency บน MySQL ผลนี้จึงไม่ใช่การรับรองความพร้อม production

ขั้นถัดไปที่แนะนำ: ป้องกันการแจ้งเติมเงินซ้ำและปรับผลตอบกลับหลังส่งฟอร์ม แล้วทดสอบ browser flow นี้ซ้ำก่อนเปิดร้าน
